Advatar EUDI Wallet · Technical Overview

Post-Quantum Web-Evidence Issuance with TLSNotary

How the EU Wallet turns a fact from a real HTTPS session into a verifiable credential: a TLSNotary prover co-signs the session with a post-quantum notary, the holder chooses exactly which JSON fields to disclose, and the issuer mints an SD-JWT web-evidence VC straight into the wallet over OpenID4VCI.

Notary: notary.euwallet.advatar.systems  ·  Issuer: vcissuer.advatar.systems  ·  Credential: SD-JWT, vct dev.advatar.tlsn.evidence.1  ·  Transport: TLS 1.2.

1 · At a glance

TLSNotary lets a holder prove “this is what the server actually sent me” without giving the verifier their credentials or a replayable session. The wallet runs the prover against a notary + proxy; the notary sees only ciphertext but co-signs a commitment to the transcript. The result is bound into a wallet credential the holder can present later — and the holder decides, field by field, what the credential reveals.

1. Notarise

The prover runs the HTTPS session with a notary that co-signs the transcript — over a post-quantum key exchange and a post-quantum signature.

2. Disclose

For JSON/API responses the holder picks which leaf fields (RFC 6901 pointers) go into the proof; the rest stay private.

3. Issue

The signed artifact becomes an OpenID4VCI offer; the issuer mints an SD-JWT web-evidence VC into the wallet.

3 · Selective disclosure — the holder chooses what to reveal representative mockup

This is the heart of the flow. When the notarised response is JSON, the wallet flattens it into its leaf fields and lets the holder tick exactly which ones become part of the proof. Everything else is withheld — the verifier learns the disclosed facts and nothing more.

Reading the screen. The holder is proving their bank account is real and in good standing — without revealing their balance, IBAN, or date of birth.

  • Disclosed — /account/status, /account/type, /holder/name
  • Kept private — /account/iban, /account/balance, /holder/dateOfBirth

Fields are addressed as RFC 6901 JSON Pointers. The default is to disclose everything; the holder deselects what to withhold. The chosen pointers are recorded in the credential's credentialSubject.disclosedFields.

Honest scope. The picker is the selection / consent surface, and the chosen pointers are recorded as disclosed. The transcript-level redaction that reveals only the selected byte-spans and cryptographically strips the rest is the remaining core work — until it lands, unselected fields are simply not listed as disclosed rather than being removed from the underlying attestation.

5 · What makes it post-quantum

A classical TLSNotary proof is only as durable as the classical crypto underneath it — a future quantum adversary who recorded the session could forge or unmask it. This deployment hardens both the key exchange and the notary’s signature with NIST PQC primitives, in hybrid mode (a classical algorithm AND a post-quantum one must both hold).

Post-quantum key exchange ML-KEM

The session key is derived from a hybrid P-256 + ML-KEM-768 agreement (P256MlKem768V1): a classical ECDH share and a lattice KEM encapsulation, combined so recording the traffic today does not let a future quantum computer recover the key.

Post-quantum attestation ML-DSA

The notary’s SignedArtifact carries a hybrid ES256 + ML-DSA-65 signature — an ECDSA P-256 signature and an ML-DSA (Dilithium) signature over the same commitment. A verifier requires both to check out.

TLSNotary here runs over TLS 1.2: the prover pins the session to 1.2 because the notary’s selective-reveal machinery operates on the 1.2 record layer. The post-quantum hardening is layered on top of that transport.

6 · The issued credential & how it verifies

AspectDetail
FormatSD-JWT VC, vct dev.advatar.tlsn.evidence.1 ("TLSNotary web evidence (development)").
What it assertsThe notarised server + the disclosed JSON fields, listed as RFC 6901 pointers under credentialSubject.disclosedFields, bound to the notary attestation.
Holder bindingIssued to the wallet's key (Secure Enclave when available, software fallback otherwise); presented later over OpenID4VP with proof-of-possession.
Notary trustThe verifier checks the hybrid ES256 + ML-DSA-65 signature against the notary's published key (tlsn.notaryKeyB64u); both components must verify.
IssuanceOpenID4VCI credential offer by value (openid-credential-offer://) handed to the wallet's normal add-credential flow.

Honest limits

  • Selective disclosure is a consent/selection surface today; transcript-level redaction (reveal only selected spans) is the remaining core work — see §3.
  • Development credential: the vct is dev-scoped; the demo path (/dev/tlsnotary/demo-offer) mints a genuine self-signed offer so the wallet loop completes without a live notary. Production uses the WASM prover ↔ notary+proxy and /evidence-offers/tlsnotary.
  • TLS 1.2 only — the notary's selective-reveal works on the 1.2 record layer.
